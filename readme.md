# Автоматизация CRUD на примере простого бизнес-приложения (C#)

## Простое бизнес-приложение

Простое бизнес-приложение отвечает следующим требованиям:

1. Читает/записывает данные в БД и выполняет несложную их обработку;
2. Нетребовательно к производительности и масштабируемости;
3. Контролирует вводимые пользователем данные;
4. Обеспечивает соблюдение бизнес-ограничений;
5. В процессе выполнения команд пользователя способно испускать события и обрабатывать их
   (простое не значит примитивное).

## Задачи разработки

Изначальная задача — разобраться в подходах и библиотеках,
используемых для разработки простых бизнес-приложений на .net.

В процессе её решения появилось видение следующего процесса:

1. Актор направляет команду на исполнение;
2. Проверка команды:
    - форматно-логический контроль;
    - соответствие бизнес-ограничениям.
3. Обработка команды:
    - Запуск вычислений;
    - Генерация внутри контекстных событий;
    - Обработка внутри контекстных событий.
4. Выпуск результатов обработки (бизнес-события) и/или
   уведомлений о возможности дополнительной обработки (триггер) вне рамок текущего контекста;
5. Преобразование триггеров в новые команды;
6. Запуск команд, вызванных триггером, на обработку (со всеми проверками), начиная с пункта 2;
7. Сбор событий из всех задействованных контекстов и возврат их актору или помещение в очередь сообщений.

В процессе поиска оптимальных подходов для автоматизации данного процесса задача эволюционировала до создания
библиотеки,
стандартизующей разработку простых бизнес-приложений.

## Структура репозитория

### Стартовый набор

Стартовый набор (`gmafffff.starterKit`) — это библиотека для стандартизации и автоматизации CRUD.
Документация о библиотеке в отдельном [разделе](./gmafffff.starterKit/docs/index.md).

### Бизнес-приложение «Бронирование номеров гостиницы»

Проекты `gmafffff.training.hotel.*` относятся к приложению-испытательному стенду.

### Вспомогательные скрипты

В папке `.\scripts` размещены следующие скрипты:

- init_prj.psq — создает новое решение с некоторыми предустановленными проектами,
  настроенными для сохранения промежуточных файлов в каталоге `%temp%\gmafffff\gmafffff.training.hotel`;
- new_prj — добавляет новые проекты в решение;
- migration.ps1 — так как промежуточные файлы не сохраняются в каталоге проекта,
  то команды миграции преднастроены в отдельном файле.

## Бизнес-приложение «Бронирование номеров гостиницы»

### Архитектура бизнес-приложения

Архитектура приложения многослойная, имеет следующую структуру:

1. Домен — реализует «глупые» сущности с логикой поведения, но без контекста.
Пример доменной сущности из реального мира — это машина, которая умеет поворачивать, ускоряться и тормозить,
но не знает когда это делать.
Если машину направить на столб, то она врежется в него без предупреждения.
2. Слой бизнес-логики — добавляет «интеллектуальные» сервисы, понимающие контекст и правила, умеющие управлять доменными сущностями.
Пример объекта бизнес-логики из реального мира — это шофёр. Он получает команду от диспетчера и самостоятельно управляет машиной.
Он знает ПДД и отвечает за безаварийную езду.
3. Слой приложения — управляет потоком выполнения, координирует работу бизнес-логики.
Пример из реального мира — это диспетчер, который выпускает машину на маршрут, обрабатывает информацию о сбоях, ведёт журнал.
4. Инфраструктура — обеспечивает связь между слоями и связь со сторонними системами.
5. Веб-апи — интерфейс доступа к функционалу приложения по протоколу HTTP.
6. Веб-сайт — пользовательский интерфейс.

#### Слой домена (domain)

1. Сущности модели — «глупые» объекты предметной области, имеют поведение и состояние, но не понимают когда это использовать;
2. DTO'шки — объекты, используемые сущностями, для обмена данными между доменом и другими слоями;
3. Форматно-логический контроль — спецификации из библиотеки Validot для DTO;
4. События домена — события, испускаемые некоторыми сущностями во время выполнения каких-либо действий;
5. Обработчики событий домена — объекты, способные обработать определённое событие домена;
6. Ошибки:
    - Коды ошибок — enum перечисление возможных ошибок;
    - Сообщения об ошибках — локализованные сообщения, соответствующие определённому коду ошибки;
7. Контракты (Интерфейсы):
    - IRepository — оперативный склад;
    - IRepositoryFactory — фабрика оперативных складов;
    - IEntityMapper* — преобразователи между сущностями и DTO.

#### Инфраструктурный слой хранения (infrastructure.data)

1. Конфигурации модели EF Core;
2. Миграции БД;
3. Реализации IRepository и IRepositoryFactory;
4. Сессии БД
    - DbContext для БД;
    - IDesignTimeDbContextFactory — для создания миграций.

#### Инфраструктурный слой преобразований (infrastructure.mapper)

1. Конфигурация Mapster;
2. Перечень интерфейсов IEntityMapper*, для которых необходимо сгенерировать реализацию;
3. Сгенерированные mappers.

#### Слой бизнес-логики (business)

1. Запросы — объекты, описывающие какие сведения необходимо получить;
2. Команды — объекты, описывающие какие действия необходимо выполнить;
3. Форматно-логический контроль — спецификации из библиотеки Validot для команд;
4. Бизнес-ограничения — предусловия, которые должны быть выполнены для выполнения команды;
5. Обработчики — объекты, способные выполнить запрос или команду;
6. События — информация об изменениях произошедших в системе для ответа отправившему команду;
7. Сигнальные события — события, на основе которых можно создать ещё одну команду;
8. Преобразователи сигнальных событий — определяют какие команды необходимо выполнить в ответ на сигнальное событие.

#### Образец данных (sampleModel)

Объекты слоя генерируют синтетическую модель предметной области.

1. Конфигурация Autofixture — для автоматической генерации данных;
2. БД для хранения синтетической модели;
3. ServiceProvider;
4. Синтетическая модель.

#### В разработке

1. Слой приложения (application) — интеграция бизнес-логики и кеширования, логирования и т.п.
2. Веб-апи;
3. Веб-сайт.

### Оригинальное тестовое задание

Реализовать систему администрирования отеля.
Требования к функционалу:

1) Система должна представлять собой web-приложение, имеющее страницу авторизации и страницу администрирования.
2) В БД системы должна иметься таблица пользователей, содержащая логины и хэши паролей.
3) Страница администрирования должна содержать таблицу номеров отеля с возможностью поиска и сортировки по различным
   полям.
4) Должна иметься операция заселения в номер при которой создается новая запись о посетителе с датой въезда.
5) Должна иметься операция выезда из номера, при которой номер освобождается и подсчитывается оплата в зависимости от
   типа номера, количества мест и времени.

Требования к предметной области:
В отеле имеется определенное количество номеров. У каждого номера имеется: вместимость — количество человек, которое
может в нем проживать, тип - стандартный, полу люкс и люкс, состояние - занят или не занят и т.п.
При въезде в номер создается запись в таблице посетитель, которая содержит ФИО въезжающего, дату въезда и дату выезда.
Для системы авторизации должна иметься таблица пользователей, содержащая логин и хэш пароля.
Прочий дополнительный функционал создается на усмотрение.

Требования к технической стороне:
Система должна быть реализована с использованием ASP.NET Core, для системы авторизации необходимо использовать её, для
работы с БД ORM Entity Framework Core. Желательно проектировать api с учетом REST. Для документации API использовать
swagger ui. Фронтенд на усмотрение. Дополнительный функционал приветствуется.
